# Audit: slice `core` (src/mesh/**, src/operators/**, src/solvers/**, src/threading.jl)

Method: full read of all ~8.7k lines (adaptivity + advection partly via two read-only scouts; their headline claims re-checked where noted), grep-verified dead-code scan (`/tmp/audit-core/dead.sh`, `dead2.sh`), and single-thread (`-t 1`) Julia measurements on a 26 368-cell, 412-block mesh (circle-refined, `block_size=(8,8)`, `max_level=3`). Items not observed are tagged [INFERENCE]. No tracked file was modified. Julia 1.12.7; threaded behaviour could **not** be measured (owner constraint: 1 thread), so all Polyester conclusions are static.

## 1. Summary
- Code is generally well-typed and validated (0 `@assert` in slice, `ArgumentError` everywhere; only 1 of 231 exports undocumented: `MimeticProjectionSolver`). Struct design is mostly concrete; hot cycles are allocation-free (V-cycle `ldiv!` 0 B / 1.05 ms, factorized `mul!` 0 B / 0.52 ms, `_smooth!` 0 B, `diffusion!` 0 B at 26k cells).
- Biggest bloat: the tree-multigrid hierarchy builder exists three times (~680 lines, geometric_preconditioner.jl / implicit_diffusion.jl / variable_diffusion_preconditioner.jl) and the "Krylov solve + stats" block three times (~135 lines); a shared plan/kernel could remove ≈350–450 lines.
- Dead/compat code: 2 dead functions + 1 dead method, 3 unreferenced compat aliases (exported), 1 trait type (`AbstractEllipticOperator`) with no methods, 2 byte-identical sparse-mul kernels, 2 byte-identical cell-index helpers (96 call sites).
- Threading: no write race found in slice parallel bodies, but the abstraction is inconsistent (5 launch APIs, a wrong docstring, serial passes between threaded ones), exceptions/user callbacks inside `@batch` are untested, and CI has no serial-vs-threaded equivalence test.
- Efficiency flags (measured): topology-change cost is large vs. a solve (`EllipticOperator` 218 ms/198 MB, `TreeGeometricMultigridPreconditioner` 183 ms/178 MB vs `solve!` 25 ms at 26k cells; reuse path 23 ms).

## 3. Details (high/med)

### C1 – shared hierarchy plan (L)
All three builders do: (1) validate, (2) decide `can_reuse`, (3) look for an `initial_matching_level` and, if found, copy the old suffix *and then repeat the same copy inside the coarsening loop* when a coarse mesh matches (`geometric_preconditioner.jl:653-678` vs `779-806`), (4) generate `coarse_mesh` via `_capped_tree_mesh`/`_all_leaf_pruned_mesh`, (5) build a prolongation, (6) assemble the physics-specific coarse operator. Steps 1-4 and the suffix bookkeeping are physics-independent. Proposed shape:

```julia
struct TreeLevelPlan; mesh::BlockTreeMesh; reuse_index::Int; end   # reuse_index>0 ⇒ suffix starts here
plan = tree_coarsening_plan(operator.mesh; pruning, coarse_size, max_levels, size_of = ncells,
                            reuse_meshes = reuse === nothing ? nothing : mesh.(reuse.operators))
for (i, level) in enumerate(plan)  # physics callback builds operator/prolongation or reuses suffix
```
`TreeStaggeredMultigridComponent`, `TreeVariableDiffusionPreconditioner` and `TreeGeometricMultigridPreconditioner` already share `AbstractGeometricMultigridPreconditioner` + `MultigridLevel` + `_vcycle!`, so only construction is duplicated.

### C15/C16 – threading review (static)
Checked every `@_parallel`/`_parallel_*` body in the slice for cross-iteration writes: `_update_elliptic_face_coefficient!` (stiffness refresh writes `stiffness_values[pointer]` by owner; the transpose-averaging loop touches each unordered pair once because it only acts when `row < column`), `_refresh_multigrid_level!`, `_refresh_smoothed_transfer!` (owner-computes via `_grouped_output_schedule`), `_smooth!`, `_vcycle!` residual/correction, sparse row-products (gather from the stored transpose), `fill_halo!` (writes only halo destinations, donors are owned cells because `_cellref_at` clamps to `1:nx,1:ny`), `_build_halo_schedule` (each entry owns `4(i-1)+1:4i` of the candidate arrays). **No write race found.** Shared mutable scratch exists but is only used serially: `GradientOperator.pressure_jump` (gradient.jl:44), `FactorizedEllipticOperator.face_input/face_output` (documented "must not be called concurrently"), `StaggeredDiffusionComponent.input/output` (staggered_diffusion.jl:216-225) and the `Ref{Any}` BC slots (C13) — fine today, but any future task-level parallelism over operators (e.g. x/y velocity solves, which the physics makes independent) will hit them; worth one sentence in the docstrings of `StaggeredDiffusionOperator`/`diffusion!` (currently only `GradientOperator`/`FactorizedEllipticOperator` say so). `_phase_transport_connectivity` (staggered_schedules.jl:173-192) mutates `mesh.topology_cache.phase_transport[Axis]` without a lock [INFERENCE: latent race only if workspace construction is ever threaded].
Nested `@batch`: `_parallel_for` (field_transfer.jl:107) → `restrict!` → `_parallel_columns` can nest, but `_parallel_columns` runs serially for `nx*ny < 1024` (any block < 32×32), so nesting is inert with default block sizes (scout flagged it "high"; downgraded here because of that guard).

## 4. Nits
- `src/threading.jl:41,63`: `_parallel_batch_size(n, n)` in `_parallel_columns`/`_parallel_block_columns` always evaluates to 1 for the tile counts used (tiles = 4·threads); the helper call is a no-op there.
- `@_parallel for i in 1:length(x)` appears ~100×; `eachindex(x)` is more idiomatic (works with the macro because `length(range)` is used).
- `Base.show(::LinearSolverStats)` (geometric_preconditioner.jl:26-45) hand-lists 11 fields; a `fieldnames` loop is 4 lines. Field/keyword naming debt: `cycles`/`max_cycles` in `solve!` count **Krylov iterations**, not multigrid cycles.
- `MultigridLevel` fields `matrix_transpose::R` and `temporary` double as row-sum scratch (geometric_preconditioner.jl:894-902) — rename or document.
- `isbalanced` (mesh.jl:903-925) is O(blocks²·9) and only used in tests; the `xshifts/yshifts` periodic-shift tuples are re-derived in `_touch`, `_balance!`, `isbalanced` (3×).
